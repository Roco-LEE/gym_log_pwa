# LLM 운동 코치 — 1단계 설계 (2026.10.06)

> **한 줄**: 집에서 PC가 엑셀 기록을 읽어 **다음 운동 계획을 LLM으로 짜고 `plan.json`에 넣는다.** 폰은 지금처럼 온라인일 때 `plan.json`을 받아 두고 헬스장에선 오프라인으로 그대로 진행.
> **핵심 원칙**: LLM은 **제안**, 증량 한도·운동 목록·부상 규칙은 **파이썬이 강제**. 오프라인 구조는 건드리지 않는다.
> 새 세션은 이 문서를 먼저 읽고 §7 순서대로 진행.

## 1. 전체 흐름

```
[집 PC]  python coach.py --date 2026-10-08 --note "허리 약간 뻐근"
   ① sync_excel.read_excel()          ← 기존 함수 재사용 (운동목록·기록·활동)
   ② build_context()                  ← 최근 기록 요약 + 파이썬이 계산한 통계
   ③ Claude API 호출 (도구 강제 → JSON)
   ④ validate()                       ← 가드레일: 고치거나 경고
   ⑤ plan.json 병합 저장 + coach_log 기록
[폰]  집 Wi-Fi에서 앱 열면 fetchPlans() 가 plan.json 받아 저장 → 헬스장에선 오프라인
```

**1단계는 앱(`index.html`)·`sw.js` 수정 없음.** 앱의 `fetchPlans()`가 이미 `plan.json`을 받아 홈 카드로 띄운다 (`index.html` 806행 근처).

## 3. 입력: LLM에 보내는 컨텍스트 (JSON)

통계는 **파이썬이 계산**해서 준다. LLM에게 계산을 시키지 않는다(틀린다).

```json
{
  "target_date": "2026-10-08",
  "request": { "focus": "하체", "note": "허리 약간 뻐근", "time_budget_min": 60 },
  "profile": { "goal": "근비대·자세 우선", "injuries": ["허리(요추) 주의"], "days_per_week": 3 },
  "exercises": [
    { "name": "레그프레스(원판)", "part": "하체", "type": "프리웨이트", "step": 10, "rep_range": "10-15" }
  ],
  "stats": [
    {
      "ex": "레그프레스(원판)",
      "last_date": "2026-10-01", "days_since": 7,
      "last_sets": [{"kg": 40, "reps": 12}, {"kg": 40, "reps": 12}, {"kg": 40, "reps": 11}],
      "last_memo": "허리 붙인 채",
      "hit_top_of_range": false,
      "best_e1rm": 56.0,
      "sessions_6w": 5
    }
  ],
  "part_last_trained": { "하체": "2026-10-01", "등": "2026-10-03", "가슴": "2026-09-29" },
  "recent_day_memos": [ { "date": "2026-10-03", "memo": "잠 부족" } ],
  "recent_cardio": [ { "date": "2026-10-04", "ex": "트레드밀", "km": 3.0, "min": 25 } ]
}
```

- **최근 범위**: 6주 또는 최근 12세션 중 짧은 쪽 (토큰 절약)
- `hit_top_of_range`: 지난번 모든 세트가 rep 범위 상단에 도달했나 → 증량 신호
- `best_e1rm`: Epley(`kg × (1 + reps/30)`), 참고용
- 오늘 메모는 `[기록]` W열의 `[오늘] …`에서 추출

## 4. 출력: JSON 스키마 (도구 강제 호출로 받음)

`plan.items` 형식은 **기존 `plan.json`과 동일**하게 맞춘다 → 앱 수정 불필요.

```json
{
  "plan": {
    "date": "2026-10-08",
    "title": "AI 코치 10/8 하체",
    "note": "허리 뻐근 → 하체 무게 유지, 자세 위주",
    "items": [
      { "ex": "레그프레스(원판)", "warm": {"kg": 20, "reps": 12}, "kg": 40, "reps": 12, "repsText": "12~15", "sets": 3, "rest": 90, "note": "지난번 3세트 11회 → 무게 유지, 12회 채우기" }
    ]
  },
  "rationale": [ { "ex": "레그프레스(원판)", "why": "3세트가 상단 미달, 허리 메모 있어 증량 보류" } ],
  "warnings": [ "허리 메모가 있어 데드리프트 제외" ]
}
```

스키마 제약:
- `ex` = **운동목록 이름 enum** (스키마에 직접 넣음)
- `sets` 1~6 (엑셀 [기록]이 6세트까지), `reps` 1~30, `kg` ≥ 0 또는 `null`(지난번 무게 그대로)
- `warm`은 `{kg, reps}` / `false` / 생략 (README 규칙 그대로)

## 5. 프롬프트 (시스템)

```
당신은 일반인 헬스 이용자를 돕는 보수적인 근력운동 코치다. 의학적 진단이나 치료 조언은 하지 않는다.
- 주어진 운동 목록에 있는 운동만 쓴다.
- 진행 규칙(더블 프로그레션): 지난번 모든 세트가 rep 범위 상단에 도달했으면 다음엔 그 운동의 step만큼만 올리고,
  아니면 무게는 그대로 두고 횟수를 채운다. 한 번에 step보다 크게 올리지 않는다.
- profile.injuries, 최근 메모, request.note에 통증·부상·컨디션 저하가 있으면 관련 부위는 증량하지 않고,
  부담 큰 운동은 빼거나 가벼운 대안으로 바꾸고, 그 이유를 warnings에 적는다.
- request.focus 부위를 우선하되, 최근 48시간 안에 한 부위는 피한다.
- 시간 예산 안에 들도록 운동 수·세트 수를 정한다 (세트당 대략 휴식시간 + 40초).
- note와 why는 한국어로 짧게, 근거가 된 지난 기록을 언급한다.
- 반드시 make_plan 도구로만 답한다.
```
사용자 메시지 = §3 컨텍스트 JSON.

모델: **저가 모델로 시작**(시작 세션에서 `claude-api` 스킬로 현재 모델 ID·요금 확인), 계획 품질이 아쉬우면 상위 모델로 올린다. 호출 방식은 **도구 정의(input_schema = §4) + 도구 강제 선택**으로 JSON만 받는다.

> **2026-10-06 확정 (claude-api 스킬 확인)**
> - 도구 강제 선택(`tool_choice` any/tool)은 Sonnet 5.5·Opus 5.5·Fable 5.1에서 **400**. → **구조화 출력**(`output_config.format` = §4 JSON 스키마)으로 변경. Haiku 4.5·Sonnet 5.5 모두 지원이라 모델은 ID만 바꾸면 됨.
> - 스키마에 `enum`(운동 이름)은 되지만 숫자 범위(`minimum`/`maximum`)는 API가 안 받음 → sets 1~6 등은 G4에서 파이썬이 강제.
> - 모델: `claude-haiku-4-5`($1/$5 per 1M)로 시작, 아쉬우면 `--model claude-sonnet-5-5`($2/$10). 1회 추정 입력 ~6K·출력 ~2K 토큰.
> - `date`·`id`는 LLM이 아니라 파이썬이 넣음. `warm: null` → 키 생략(지난번 워밍업대로).

## 6. 가드레일 (`validate()` — LLM 뒤에서 파이썬이 강제)

| # | 규칙 | 위반 시 |
|---|---|---|
| G1 | `ex`가 운동목록에 있음 | 그 항목 삭제 + 경고 |
| G2 | `kg` ≤ 지난번 최고 세트 무게 + step | 상한으로 깎음 + 경고 |
| G3 | 부상·통증 키워드(허리·통증·아픔·뻐근·부상)가 profile/메모/요청에 있으면 해당 부위 운동은 증량 0 | 지난번 무게로 되돌림 + 경고 |
| G4 | `sets` 1~6, `reps` 1~30 | 범위로 자름 |
| G5 | 예상 시간 ≤ `time_budget_min` × 1.2 | 뒤 항목부터 세트 축소 + 경고 |
| G6 | 같은 날짜에 이미 끝낸 운동(오늘 기록)과 중복 | 경고만 |
| G7 | 지난번 rep 범위 상단 미달이면 `kg` ≤ 지난 무게 (2026-10-06 추가) | 지난 무게로 되돌림 + 경고 |

> **2026-10-06 구현 메모**
> - **G7 추가 이유**: 첫 Haiku 실행에서 상단 미달 운동 3개를 +step 증량 → G2(지난+step 이하)는 통과시킴. 컨텍스트에도 파이썬이 계산한 `next_kg_max`를 넣어 LLM이 계산하지 않게 함 → 재실행 시 위반 0.
> - **G3 해석**: `profile.injuries`는 늘 있는 지병이라 근거로 쓰면 영영 증량이 안 됨 → LLM 맥락으로만. G3 근거 = 오늘 요청 + 최근 7일 그날 메모(부위 단위) + 그 운동의 마지막 메모(그 운동만). '통증 없음'처럼 뒤에 '없'이 오면 부정으로 봄. 부위어 매핑: 허리→하체·등·코어, 무릎→하체, 어깨→어깨·가슴·등, 팔꿈치·손목→팔·가슴, 부위어 없으면 전 부위.
> - **G4 예외**: 플랭크처럼 rep 범위가 초(30-60초)인 운동은 reps 상한을 그 범위 상단까지.
> - 테스트: `python -m unittest discover -s tests -v` (19개, 규칙을 꺼 보면 해당 테스트가 실패하는 것 확인).

검증에서 고친 내역은 `warnings`에 `[자동수정]` 접두로 붙여 **앱 카드의 note에 보이게** 한다 → 사람이 판단.

## 7. `plan.json` 병합 규칙

- AI 계획 `id` = `ai-YYYY-MM-DD`. 같은 id가 있으면 **교체**, 손으로 쓴 계획(다른 id)은 **유지**
- 지난 날짜 계획은 그대로 둔다(앱이 "밀린 계획"으로 2주간 보여 줌)
- 쓰기 전 `plan.json` → `백업/plan_YYYYMMDD-HHMM.json` (기존 백업 폴더 관행)
- `--dry-run`: 출력만 하고 파일은 안 씀 (기본으로 먼저 이걸로 확인)

## 8. 진행 순서 (새 세션 체크리스트)

1. ✅ **서빙 차단 목록**을 `serve.py`에 추가 + `.gitignore`에 `coach_profile.json`, `coach_log/` 추가
2. ✅ `coach.py` 뼈대: `read_excel()` → `build_context()` → **LLM 없이 컨텍스트만 출력** (`--context`)해서 통계가 맞는지 눈으로 확인
3. ✅ LLM 호출 + 도구 스키마 → `--dry-run`으로 계획 출력
4. `validate()` G1~G7 + 단위 테스트(가짜 LLM 출력으로 규칙별 1개씩) ✅ 2026-10-06
5. `plan.json` 병합 저장 → 폰에서 카드 뜨는지 확인 → **실제로 2~3회 이 계획으로 운동**
6. `coach_log` 쌓기 (나중 Eval 정답 세트 재료)

**1.5단계(선택)**: `serve.py`에 `POST /api/coach {date, focus, note}` → `coach.make_plan()` → `plan.json` 저장 후 계획 반환. 앱 홈에 "AI 계획 받기" 버튼(온라인일 때만), 성공하면 `fetchPlans()` 재호출. API 실패·오프라인이면 기존 계획 그대로(fallback) + 토스트.

**2단계 이후**: Eval(고정 입력 세트로 규칙 위반률 측정) → 도구 호출(LLM이 `get_history(ex)`를 직접 조회) → MCP 서버(헬스일지를 Claude에서 질의) → 현장 컨디션 조정.
